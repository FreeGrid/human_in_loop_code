# Plan operation integrity and recovery

Every Plan write validates the whole candidate before persistence: fatal UTF-8 decoding, Unicode scalar safety, scalar YAML schema, ordered nonoverlapping section markers, canonical execution records and scalar roundtrip. Draft completeness and signed execution authority are separate transition checks. Historical V1 records remain readable; reading never invents missing evidence or replaces a baseline.

`operation_runtime` binds a Plan to its canonical Controller runtime directory. The trusted host sets `PI_PLAN_RUNTIME_ROOT` before loading the extension; otherwise it uses the user's `.local/state/pi-plan/operations` directory. New Plans bind immediately. A legacy Plan without execution records can bind through explicit reconciliation. A legacy Plan with existing execution records cannot silently bind or recapture a baseline. Runtime data must be outside target repository content. A different configured namespace fails closed.

Each canonical Plan path has a SHA-256-named runtime directory containing immutable numbered canonical JSON events and validated candidate bytes. Events form a hash-linked append-only chain under an exclusive journal lock. `operation-journal.schema.json` defines the machine envelope. Each operation starts with intent, then an exact candidate prepare, and a commit after atomic installation and directory synchronization. A failure records the known checkpoint and possible side effects. A blocked finalize summary is a committed `blocked_projection`; it is not completion. No one-shot capability or signing key is serialized in the journal.

A filesystem error after installation yields `operation_recovery_required` and an operation ID. It never reports successful application without durable commit evidence. A commit-link synchronization failure may leave a valid commit followed by explicit uncertain failure; that sequence remains inspectable. Source bytes, candidate hashes, original execute/baseline references and events are preserved. A phase-start intent without commit or explicit recovery blocks another capture.

Recovery first inspects exact current bytes and journal head without changing anything. The Human capability binds that inspection, operation ID and action payload. Recovery persists its consumed authorization receipt. Exact candidate bytes plus candidate prepare can be confirmed without rerunning any gate or capture. Exact original source bytes permit an explicit abort; external side effects may still need fresh verification. Different bytes, corrupt records, missing candidates or unknown lock ownership fail closed. Recovery never rolls back content, applies migration, starts another phase or signs old evidence.

Locks retain their existing zero-byte Plan/finalize format; ownership is recorded by canonical path and inode in the external journal. A live writer's lock cannot be recovered. A settled writer can attest quiescence through an opaque process-local owner token. After a process crash, recovery requires the recorded process to be demonstrably absent; reused/live PIDs fail closed. A fully synced owner record is hardlinked into the external append-lock path, preventing an empty public-header window. An unknown legacy lock or a crash before any durable operation identity requires an offline operator to inspect the preserved evidence with writers stopped; no timeout guesses or automatic lock stealing are performed.

The journal provides cooperative-writer crash integrity, not a sandbox against an actor able to rewrite every local file and recompute hashes. Filesystem atomic rename/link and synchronization semantics are platform assumptions. Reads never repair files, remove locks, normalize metadata or recapture baselines.

There is an explicit pre-intent boundary: the process may acquire the zero-byte Plan lock and publish an append owner, then die before its first durable intent event. In that case there is no new operation ID to recover automatically. The unknown Plan lock and source bytes remain preserved, and automatic recovery refuses to guess ownership. An offline operator must stop all writers and inspect the lock/source evidence before removing an orphan; this action must not replay a gate or baseline capture. Once an intent exists, read-only operation enumeration can recover its ID even when the host never returned a response.
