### Lightweight documentation synchronization

Update related documentation when an implemented user-visible behavior stabilizes; check for omissions once before completing a major task or delivering a PR. Do not check after every child task or wait for the whole Plan to finish. During unsettled requirements, update the Plan first. A pause does not require forced documentation cleanup; disclose a known gap briefly when relevant.

Use the task or delivery slice's related changes, not merely the current uncommitted diff. Prefer exact PR base/head commits or an explicitly selected commit range. For a stacked PR, compare with its own parent/base, not main repeatedly. For a multi-PR delivery, also examine the net delivered behavior. Include related local changes not yet in the PR and exclude unrelated dirty work. PR descriptions help navigation; actual code and current documentation are the basis for judgment. If the delivery range is ambiguous, resolve that ambiguity rather than claiming coverage.

Start with changed filenames. Follow small explicit source-to-document mappings, relevant imports/callers/config readers, and literal references to command names, configuration keys or interfaces in documentation. Read only the needed diffs, code context and document sections. Follow a dependency further when it could change user-visible behavior; do not build a permanent whole-repository dependency graph or assume an absent match means no documentation impact. A dependency PR's earlier check does not approve changes introduced by its dependents.

Update existing explanations and examples, replacing obsolete content. Internal changes without user-visible effects need not change documentation. Do not create extra documents, default documentation subtasks or a separate Agent just to satisfy a workflow. Use a separate documentation task or Agent only when the work warrants it. Do not append work logs, synchronization status, verification details or results to the readable Plan.

Ordinary editing remains available without a Harness. Optional delivery checks provide candidate locations and unresolved questions, not proof of semantic correctness. Reuse a check only while its relevant commits, code, documents, mappings and search domain remain unchanged; new relevant changes invalidate it, and unresolved issues remain open. Never treat a touched README, an empty candidate list or a prior PR check as proof that documentation is correct. Report actual omissions or failures; no fixed "no documentation changes needed" response is required.
