# Human-in-the-Loop：把研究的方向握在自己手里

一个研究想法刚冒出来的时候，最让人兴奋的，是赶紧把它做出来试试。

你可能只发了一句：“帮我写一个 100 行以内的 C++ 匹配算法。”模型很快给出了程序。你接着让它补测试、试几组数据、找些参考资料，顺便想了想论文怎么写。原本还停在脑子里的事情，开始变成屏幕上的代码和结果。

然后，你想把成果拿给别人看，才发现还得花些时间理顺：哪份代码是现在要用的，哪条需求已经改过，哪些文件只是临时实验。模型已经往前跑了好几步，你却还在找一个能重新接住项目的位置。

我们希望，最开始那份“我想试试”的兴奋，能一直持续到成果交出去的时候。

**Human-in-the-Loop 是一套围绕科研工作设计的 Pi 扩展。** Pi 是让 AI 助手在终端里读文件、写代码、执行任务的工具；这套扩展帮你把计划、代码、验证和论文安排清楚。你用熟悉的语言讲想法，在看得懂的地方作决定，然后让助手继续往前做。

## 从第一天起，让每份工作都有个家

先给那个小小的匹配项目留出两个位置。通过[仓库分离](extensions/control-init/README.md)，程序住在 `code` 仓库里，连同运行所需的资源和给使用者看的说明。计划、测试、参考资料、实验核对和过程记录，则放进自己的 `control` 仓库。

这件事很朴素，却会在项目越做越大时省下许多心思。你可以放心保留一次失败的尝试、一份还没整理好的资料、一段用来排查问题的脚本。它们都是研究的一部分，有自己的地方，也有自己的版本记录。

等到分享代码时，交出去的是一份可以独立运行的程序仓库。别人从使用说明开始，你从 control 里的研究过程继续。一次代码提交，也就用不着顺带考虑论文草稿和实验日志该怎么藏好。

已有工程也可以慢慢整理成这样的结构。过去积累下来的东西可以保留，接下来的工作有了清楚的去处。

## 在代码长出来之前，先看懂要做什么

目录安顿好了，我们回到那个百行算法。

真正需要你把关的，往往发生在第一行代码写下去之前：输入究竟是什么，结果要交给谁用，哪些情况这次要支持。模型很擅长把一句话继续往下展开，而其中的一些细节，可能恰好偏离了你的本意。越早看到这些差异，调整起来越轻松。

但计划也有写过头的时候。在一次真实的 KM 算法试用里，一个“100 行以内的 C++ 实现”请求，最后得到了约 135 行 Plan。目标、策略、验收和验证把同一个要求讲了好几遍，前面还在询问是否支持负权，后面已经把它当成了确定条件。为了看懂一个小程序要做什么，人先得读完一份比预期程序还长的计划。

这次经历让我们把 [Plan](extensions/task-plan/README.md) 重新做得简单：**一份当前有效的需求，加上一棵跟着工作推进的任务树。**

Plan 按需使用。独立小请求，例如回答问题、读文件、运行命令或等待，可以直接完成，无需创建 Plan，也无需先调用 `plan_set_mode`。即使已有选中的 Plan，也不会自动把新请求纳入其中；只有你要求规划，或上下文明确定义为当前 Plan 的工作，才进入 Plan 流程。

眼前准备做的事，写到足够开始；接下来几步，补上已经想清楚的细节；更远的方向，先留个轮廓。这就是这里的 rolling：走近一项工作时，再把它看清楚。一个小需求可能只有一个大任务，足够表达意思就很好。

做完一项，就把它勾起来。子任务也留在原处，回头翻看时，你还能知道当时做了哪些事情。运行结果和测试记录留在 control，Plan 保持短小，把你的注意力留给当前的需求和进度。

这里最值得你亲手做的一件事，是在开始之前，把需求和每一条任务从头到尾读一遍。即使不熟悉 C++，你也能判断“只输出总分”还是“还要输出每一组配对”才符合自己的用途。把这一点想清楚，助手写得越快，你就越能用上它的速度。

## 想法变清楚了，就在原来的地方接着改

等程序真正跑起来，你发现后续实验只需要总分，配对明细暂时用不上。这是使用之后才会得到的认识，很正常。

在这个 Plan 的工作范围内，告诉助手以后，继续改的是眼前这份 Plan：输出要求换成新的，受影响的工作跟着调整，其他进度尽量保留。即使已经做完的功能需要返工，也能在原来的任务树里找到位置。想法一点点变清楚，文件也跟着变清楚。

第二天回来，打开它，你看到的是现在要做的事、已经勾好的进度，以及接下来那一步。换个模型会话接手，也有同一份文件可读。昨天的聊天可以很长，今天继续工作的起点依然很短。

## 后来，同一份代码长出了两篇论文

研究继续推进，你开始有了两个写作方向：一篇讨论方法，另一篇关注应用。两篇文章共用这份实现，各自又有不同的图、引用和修改节奏。

这时，为每篇文章准备一个独立的论文仓库就很自然。第一篇在改审稿意见，第二篇还在调整结构，代码也可以继续修复和完善，三份工作各自保留自己的历史。

```text
matching/
├── matching_control/         计划、测试、资料和研究过程
├── matching_code/            程序、运行资源和用户说明
├── matching_paper_a/         第一篇论文、引用、图和投稿材料
└── matching_paper_b/         第二篇论文，使用同一份代码
```

工具里把论文仓库称为 LaTeX 仓库，LaTeX 是科研中常用的论文排版方式。你可以先把它理解成“这篇文章自己的工作空间”。正文和相关材料在这里慢慢完成，文章之间保持独立，成果又能引用同一份代码。

等到投稿、分享或开源，研究过程仍然完整地留在你手里，准备交付的部分也已经有了清楚的边界。收拾项目终于成了平时顺手做的事。

## 项目大了，让助手沿着线索找到重点

到了准备交付的时候，同事会按照 README 运行程序。你已经把输出改成了总分，说明里的例子也要跟上。这个改动看起来很小，可能却同时出现在入口说明、功能文档和某个调用它的地方。

如果每次都让模型从头翻整个仓库，时间和上下文会花在很多重复阅读上。我们更愿意让它先拿到一条有用的线索：这次到底准备交付哪些修改。

PR，也就是把一组修改交给人审阅的申请，正好能提供这样的入口。沿着相关提交找到改动的文件，再顺着功能说明、配置项和调用关系往下看，需要哪些内容，就补哪些内容。模型少读一些无关文件，你也少等几轮“我先看看这个项目”。

文档就在这样的节奏里跟着工作一起更新。想法还在讨论，先改 Plan；接口已经稳定，把对应说明和例子补好；准备交付时，再回看相关变化有没有漏下的地方。可选的 [DocSync 助手](extensions/task-plan/docsync/delivery.md)会帮忙找出候选位置、留下还没弄清的问题，让后续阅读有个着落。最后把说明和实际行为对一遍，交给别人的用法才真正连得起来。

## 需要更多帮手时，再让团队长大一点

一路做下来，你也会慢慢知道，哪种模型更适合自己的工作。

有的模型适合一起梳理需求，有的适合持续写代码，还有的适合停下来挑问题。Pi 中的 Task Plan 可以分别指定规划、执行和审阅阶段使用的[模型与思考设置](docs/models.md)。你也可以让三个阶段都使用同一个自部署模型，先按手头的资源把工作做起来。

当几件事确实可以分开，再交给[几个 Agent](extensions/collaborating-agents/README.md)，也就是各自工作的 AI 会话：一个调查资料，一个检查实现，一个专门读文档。你能查看它们的状态、消息和交接结果，再把各自的发现放回同一个项目里判断、取舍。

默认 `/control:init` 生成 native 协作规则：Pi 使用本包的协作工具，Codex、Claude 使用各自的原生机制。希望统一用 Herdr 时，可选用 [`/control-init-herdr`](extensions/control-init/README.md#用-herdr-管理子-agent)；该模式下，创建、通信、等待和结果收集都按 Herdr skill 操作，不使用 Pi 的 `/subagent`、`/agents` 或 cmux 协作流程。初始化只生成规则，不安装 Herdr 或启动子 Agent。

那些重复又容易漏掉的动作，也可以让程序帮忙。通过任务工具记录进度、修改定义时，程序会汇总父子状态、保留子任务，并重新打开受影响的工作。更严格的项目还可以接入 [Harness](docs/harness.md) 的执行、真实验证与独立审阅服务，让正式完成有明确的检查依据。这些能力按项目需要逐步加入，开始时先用仓库分离和普通 Plan 就很好。

研究的判断仍然在你手里，助手承担起越来越多具体的工作。

## 从你现在最想试的那个小问题开始

也许是一个算法、一段数据处理流程，或者一个已经拖了很久的小实验。把它写成几句自己的话，直接让助手处理；需要先理清需求时，再一起整理成一份能读完的计划，完成第一项。

下一次打开项目时，你知道代码放在哪里，知道想法走到了哪一步，也知道接下来可以继续做什么。然后，就能把注意力放回那个最初让你好奇的问题。
