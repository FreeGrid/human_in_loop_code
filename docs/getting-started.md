# 从零开始：和助手一起完成 matching 项目

[返回首页](../README.md) · [仓库与论文指南](../extensions/control-init/README.md) · [遇到问题](troubleshooting.md)

假设你准备做一个与匹配算法有关的研究，先需要一段不超过百行的 C++ 程序：把两组对象一一配对，让总得分尽可能高。你希望模型帮忙写代码，却不希望几轮讨论之后，程序旁边堆满计划、测试记录和论文草稿；更不希望它写完一大堆东西，你才发现双方理解的需求不同。

我们就从这个名为 matching 的小项目开始。第一天，让助手能工作，建立仓库，把需求说清，再完成一小步；第二天，带着同一份计划回来，检查实现。等程序要交给别人用、研究开始形成论文时，再引入文档、协作和更强的检查。你可以跟着主线操作，也可以先读完后半段，知道项目长大后该怎么继续。下面的结果是操作时应核对的现象，并不表示你的环境已经验证通过。

## 先让助手在电脑上工作起来

先分清你接下来会用的两个输入窗口。**终端**用来启动程序，macOS 可以打开“终端”应用，Linux 使用自己的终端。**Pi**是在终端里运行的助手界面，负责连接模型，并让模型调用读写文件、执行命令等工具。这样的模型会话也叫 Agent。安装 Pi 不会自动提供模型账号或运行模型的服务器，你仍需要一个可用的模型服务。

下文标为 `bash` 的代码在终端执行；标为 `text` 且以 `/` 开头的命令，在 Pi 输入框里输入；普通中文示例则是直接对助手说的话。比如 `cd` 是终端里切换目录的命令，`/control:init` 是进入 Pi 以后才使用的命令。

先安装 [Node.js](https://nodejs.org/en/download) 和 [Git](https://git-scm.com/downloads)。Node.js 提供运行 Pi 的环境，也带有下面要用的 `npm` 安装命令；Git 为文件保留版本记录。这里采用已验证目录切换的 Pi **0.84.4**，要求 Node.js **22.19.0 或更高版本**。本文终端示例按 macOS/Linux 编写，Windows 用户先看 [Pi 的平台说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/windows.md)。

```bash
node --version
git --version
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@0.84.4
pi --version
pi
```

看到 Pi 界面后，输入 `/login`，选择你已有账号支持的提供方并登录；也可以按提供方说明设置 API Key。接着用 `/model` 选择可用模型，发一句普通问题，确认能收到回答。自部署服务先在 `~/.pi/agent/models.json` 登记地址和模型，具体例子见 [模型指南](models.md)。`~` 是你的用户目录，真实密钥不要放进项目。安装与登录细节可对照 [Pi 官方入门](https://github.com/earendil-works/pi/tree/main/packages/coding-agent#quick-start)，本文的版本依据不代表所有历史或未来版本。

能聊天之后，退出 Pi，回到终端安装本工具包：

```bash
pi install https://github.com/FreeGrid/human_in_loop_code
pi config
```

在配置界面确认 `control-init`、`task-plan`、`collaborating-agents` 三个扩展，以及 `collaborating-agents-system` 技能已启用。扩展增加命令和工具，技能提供协作说明。按 `Esc` 离开配置。以前装过 Pi 示例 `plan-mode` 的话，在这里禁用那一项，避免两个计划功能同时介入；其他无关扩展不必停用。配置操作见 [Pi 包管理文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)。

如果你已经下载了本仓库，也可以把安装来源换成 `pi install /绝对路径/human_in_loop_code`，两种来源选一个即可。历史 npm 名称 `@baochunli/pi-collaborating-agents` 和原上游地址可能还没有本文的新功能，因此这里统一使用 FreeGrid 的 Git 来源。

第一次体验，先让规划和执行都沿用你刚选好的模型。在终端重新启动：

```bash
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

这行命令只对这次启动关闭 Task Plan 的**自动模型切换**，Plan 和 thinking 都仍然可用，也可以在 `/model` 手动换模型。不加这个设置时，扩展默认尝试阶段预设中的自部署 Qwen 标识；如果你的 Pi 没有登记它，会提示切换失败并保留当前模型。后面有需要时，我们再配置三个阶段。

现在输入 `/control:status`、`/plan:status`，再打开 `/agents` 看一眼，按 `Esc` 返回。尚未建立工作空间或 Plan 的提示可以是正常结果，“未知命令”则说明扩展还没加载，需要检查安装来源、开关和是否重启。接着让助手做一件很小的实事：

```text
请实际调用 shell 工具运行 pwd，原样展示返回的目录，不修改文件。
```

你应当看到工具调用和真实目录。只有文字回答“我在某目录”，还不能说明文件工具能正常工作。能聊天却调用不了工具时，先检查模型连接、认证和工具调用配置；命令不见了则从 [排障入口](troubleshooting.md#输入命令没有出现功能) 开始。接下来每次检查，我们也会这样把助手的回答与实际返回放在一起看。

## 第一天，先给 matching 建一个清楚的家

助手已经能调用工具，现在可以安排项目文件的归属了。退出 Pi，在终端建立一个容纳项目的父目录，然后从这里启动：

```bash
mkdir -p ~/research/matching
cd ~/research/matching
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

在 Pi 输入：

```text
/control:init
```

选择 `Recommended — control + code`，再选择从工作空间名称创建仓库，名称填 `matching`，不用加角色后缀。向导将准备同级的 `matching_control` 和 `matching_code`：前者放计划、测试和研究过程，后者放程序、运行资源和给使用者看的说明。此时还没必要为将来的每篇论文准备目录。

走到最后的预览时，先看实际路径。假如发现自己从错误的目录启动了 Pi，就取消这次初始化，回到正确位置再来。取消后，本次原本准备创建的两个目标目录和规则文件不应出现；不要通过删除已有工程来重试。路径正确时选择 `Apply the shown initialization`。若出现 `preview-stale`，表示预览后的相关状态发生了变化，需要重新读取和审阅预览。

如果 matching 本来就是一个已有代码工程，这一步改选“使用已有目录”，给出 control 和 code 的实际路径即可。绑定前记下几个已有文件及 `git status --short` 中的改动，绑定后再对照：原文件和未提交改动应保留，不应被另一份同名代码替代。已有非 Git 目录经明确批准后可以新增 Git 元数据。初始化负责建立归属，旧工程里已经混放的材料仍要另行安排整理。

应用成功后，Pi 应续接当前会话并进入 control。运行 `/control:status` 和 `/control:doctor`，确认两份仓库路径正确，阅读任何路径、身份或规则问题。再让助手实际运行 `pwd`，并用相对路径读取 `CONTROL_INDEX.json`：前者应返回 control 目录，后者应读到当前工作空间的仓库关系表。这一步能发现“关系表写对了，工具却还在旧目录工作”的情况。

还可以另开一个终端窗口，查询两份仓库的根目录：

```bash
git -C ~/research/matching/matching_control rev-parse --show-toplevel
git -C ~/research/matching/matching_code rev-parse --show-toplevel
```

两次应返回各自的完整路径，而非同一个父目录。control 中应有关系表和给助手阅读的 `AGENTS.md` 工作规则；新建 code 中不应因初始化多出 Plan、测试证据或论文草稿。没有第一条提交、没有 GitHub 远端都正常：初始化只准备本地仓库，没有替你提交、推送或开源。

若你是用自然语言要求创建工作空间，模型工具不能在执行中直接替换会话，完成后按提示输入 `/control:enter`。斜杠向导完成后未能进入时，也可以明确运行 `/control:enter /完整路径/matching/matching_control`；重新核对 `pwd`，再往下走。

## 写代码前，先确认它理解的是同一件事

目录安排好了，我们终于可以说需求。KM 是这个例子采用的匹配算法；即使你不熟悉它，也可以对照输入、输出和边界，判断模型有没有擅自增加东西。在 Pi 输入：

```text
/plan 实现一个不超过 100 行的 C++17 单文件 KM 程序，求 n×n 完全二分图的最大权完美匹配。整数权值允许负数。输入 n 和权值矩阵，输出总权值和匹配结果。不支持缺边、非方阵和非完美匹配。先做计划，暂不写代码。
```

这里的方阵表示两侧对象数量相同，“完全”表示每一对都有权值，“完美匹配”要求每个对象都配上。允许负权很关键：即使所有得分为负，也要完成配对，不能靠不匹配得到零分。

打开工具返回的实际 Plan 文件。它在 control 的 `plans/` 下，名字可能类似 `001-km.md`，以返回路径为准。**把当前需求和每一条任务完整读一遍。** 单文件、C++17、100 行以内、负权和输出要求都应能找到；额外的规模上限、性能报告或 README 交付任务，需要有真实需求依据。发现偏差就先改，例如告诉助手“仍然修改当前计划，不需要性能报告，也不要增加额外用户功能”。你说了暂不写代码，code 的实际文件和 Git 状态就不应出现提前实施的变化。

这份文件应只有必要的格式标识、标题、当前需求和两层以内的 checkbox 任务树。眼前工作要明确，近期任务可以逐渐细化，远处保持粗略；小需求只有一个大任务也完全有效。它不应在需求后又重复追加 Strategy、Acceptance 或验证记录。程序生成代码的速度可能远快于你阅读的速度，所以此刻读懂这份短计划，比做完再纠偏更省心。格式和完整例子见 [Task Plan 指南](../extensions/task-plan/README.md)。

## 先做一小步，再看它是否真的完成

计划已经符合你的意思，现在另行授权实施。为了看清进度如何发生，第一次可以把停点说得很具体：

```text
按当前计划开始执行。实现放在 code，测试与验证放在 control。
先完成当前第一个有实际意义的子任务，用进度工具记录，然后停下来让我查看。
如果这项工作不需要子任务，不要为了演示硬拆。
```

如果当前大任务有几个子任务，完成第一个后，文件中应是这一项 `[x]`，整个大任务因为还有工作未做，保持 `[ ]`，其他条目不变。`/plan:status` 显示大任务的短进度，子任务状态要看实际 Markdown。确认这一步与实际工作一致后，再让助手继续剩余工作。自然语言“继续”依赖模型调用正确工具；如果它只解释而没有行动，输入：

```text
/plan:next
```

这个命令给助手当前需求、任务和下一项工作，不会瞬间完成任务。通过进度工具勾选最后一个待办子任务时，程序会自动勾选所属的大任务，**已完成子任务的文字和顺序仍然保留**。接下来轮到文件中第一个未完成的大任务，就在原位置补充需要的细节。你不需要阅读“第二轮计划”，也不会在完成项下面看到一段新增的结果总结。

随着核心算法和输入输出具备运行条件，让助手展示真实的编译命令和返回。编译器把 C++ 源文件变成可运行的程序；环境中缺少支持 C++17 的编译器时，应先报告并处理，不能把没有运行说成通过。测试脚本、临时验证产物和过程记录留在 control。然后把下面的数据送入程序：

```text
2
-1 -4
-3 -2
```

只有两种完整配对，得分分别是 `-1 + -2 = -3` 和 `-4 + -3 = -7`。因此当前程序应输出最大总权值 **-3**，并输出第 1 行配第 1 列、第 2 行配第 2 列；若接口从 0 编号，则是 0→0、1→1。这个答案可以直接算出来，不必先相信助手的“测试通过”。

假如它输出了 0，你就抓住了一处真正影响需求的问题：程序可能绕开了负权或没有完成全部匹配。把实际失败返回交给助手，相关工作继续保持待处理；已经误勾的条目应重开，修复后再运行。通过进度工具重开一个子任务时，所属的大任务也应重开，其他已完成的子任务保留。你可以直接在原 Plan 看出哪里还需要修复。

普通 `[x]` 是当前认为完成，人也可以勾选，它本身不认证测试。比如 `/plan:task T001 done` 只记录这个大任务完成，不替你勾选其子任务，其中 T001 要换成实际任务 ID；外部编辑器也不会自动经过工具的汇总规则，具体见 [状态规范](../extensions/task-plan/v3-format.md)。不要为了试按钮勾掉真实待办，也不要把编译成功或一个样例正确当作全部验证：单文件、行数以及其余输入边界仍要按需求检查。验证结果放进 control 的执行记录，Plan 只保留需求和进度。

## 用起来才发现，输出可以更简单

看到第一次结果后，你发现后续批量实验只会读取总得分，暂时不需要配对明细。需求在使用中变清楚很正常，接下来直接修改同一份 Plan：

```text
/plan:edit 现在只输出最大总权值，不再输出匹配结果；其他要求保持不变。修改当前计划，先不执行。
```

回到原文件，看路径和 `plan_id` 是否没变，旧的输出要求是否被替换。这里应只保留一份当前理解，不能前面要求配对、后面又说不用输出。受影响的输入输出工作需要调整；如果它已经完成，通过工具重新定义后应重开，不再沿用旧的完成判断。未受影响的算法进度应保留；影响范围实在不明确时，可以先保守重开，再让人核对。

助手的回复应让你容易看出变化，而不必重新打印整份 Plan。现在再授权它实现这项修改，并重跑刚才的输入：总权值仍应为 -3，但按新需求已不再要求配对输出。实现稳定后，若 code 已有输入输出说明，也应在此时更新对应段落，不能继续展示旧接口。即使这份 Plan 曾经全部完成，补充相关需求也应继续改它；明确新开另一项工作时，才使用 `/plan:new`。

## 第二天，从同一份 Plan 接着做

今天可以先停在这里。记下 control 和 Plan 的实际路径，退出 Pi。第二天从终端直接进入原 control，再启动即可：

```bash
cd ~/research/matching/matching_control
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

如果已经从别处启动了 Pi，在 Pi 中输入完整路径：

```text
/control:enter /完整路径/matching/matching_control
```

把示例换成机器上的真实路径。刚初始化的同一会话可以省略路径，重启后应明确提供；已建立的工作空间不用再次 `/control:init`。若你用 `--no-session` 关闭会话保存，无法通过持久会话续接切换目录，按提示回到终端用 `cd ... && pi` 重新启动即可。

进入后，先让工具实际运行 `pwd`，确认仍在 control，再用 `/plan:open plans/001-km.md` 选择昨天那份文件，文件名换成实际值。这一次先不让它写代码：

```text
阅读 AGENTS.md 和刚打开的 Plan，不依赖昨天的聊天，复述当前需求、
已完成项和下一项工作。先不要执行。
```

回答应知道现在只输出总权值，也应保留昨天完成的子任务，而不是回到最初的接口或另建计划。你可以把它和文件逐项对照。如果新会话必须靠猜才知道下一步，就先把缺失的当前理解补进原 Plan。确认正确以后，有待办再输入 `/plan:next`；全部完成时它应说明没有待办，不应凭空制造任务。这样，继续工作依靠的是一份能读懂的文件，而非恰好没丢的聊天记忆。

## 准备给别人看，换一个角度检查实现

接下来你想把程序给同事用，便需要从“实现者认为写好了”转向“别人能否发现问题”。先在当前会话输入 `/plan:review 关注负权、完美匹配和当前输出要求`，让助手读取真实改动，报告具体问题。它应提供文件位置和理由，不应一边审阅一边修改代码或勾选任务。

到这里，规划、执行和审阅三个阶段都有了明确用途。前面一直用 `PI_TASK_PLAN_MODEL_SWITCH=0 pi` 启动，它们应沿用手选模型，不被 Task Plan 自动切换。如果你希望分开配置，现在再按 [模型指南](models.md) 登记真实可用的模型、设置阶段变量，并从加载了新环境的终端启动 Pi。启用切换后，分别在实际需要的 `/plan:edit`、已授权的 `/plan:next` 和 `/plan:review` 中观察 Pi 显示的模型及 thinking 设置，应该对应 planning、normal、review。

三个阶段用同一模型时，名称不变很正常；预设 ID 或认证无效时，应有通知并保留当前模型，普通工作仍可继续。自部署 Qwen/vLLM 用户还要注意，当前映射中 high 和 medium 都打开 thinking，并不对应两份不同的推理预算。是否真正按预期思考，需要核对实际请求和服务日志，不能只看标签。

换模型的普通审阅仍在当前会话里。如果此时需要另一个会话单独检查负权，才把这项范围明确的工作分出去：

```text
/subagent 阅读 ../matching_code 中的 KM 实现，只检查负权处理，报告具体位置和理由，不修改文件。
```

在 `/agents` 应能看到这个子任务的运行名称和状态，原会话最终收到答复。对照它引用的文件和理由，并确认只读任务没有改动文件；返回结果还需要你或协调者判断，叫 reviewer 也不自动等于已经独立验证。

需要追查时，让助手用该次返回的 Run ID，也就是这次子任务的运行编号，查询 `session` 或 `tail`，不必扫描所有聊天。刚启动显示 `session pending` 可以等登记完成；一批任务包含多个子 Agent 时，要选具体 Run ID。普通后台运行就能体验分工，只有已配置 cmux 且主 Pi 在其中时再用可见面板，详见 [协作指南](../extensions/collaborating-agents/README.md)。

如果几次使用后，你发现模型总会忽略真实失败，或团队要求验证和独立审阅缺一不可，再考虑受治理 Harness：由程序约束执行、验证和最终接受。普通安装下 `/plan:governed status` 报告未配置是正常的，不影响继续使用 Plan。接入的团队应在隔离环境检查“验证失败、授权失效或缺少独立审阅时，finalize 必须失败”。它需要可信宿主和真实验证服务，不能靠一个通用开关补齐，具体见 [Harness 的范围](harness.md) 和 [受治理步骤](../extensions/task-plan/v3-governed.md)。

## 同一份代码，开始支持两篇论文

假设后来研究有了两个写作方向：一篇介绍匹配方法，另一篇用它分析应用数据。程序仍是同一份，你希望两篇文章各自改稿、各自投稿，不把稿件塞进 code。现在回到 control，在 Pi 中运行：

```text
/control:update
```

选择 `Add one paper repository`，给第一篇填短 ID `paper-a` 和具体路径，例如 `~/research/matching/matching_paper_a` 对应的完整路径；第二篇同样添加 `paper-b`，使用另一个目录。每次先看预览，路径错了就取消；已有工作空间取消更新后，原关系表和 `AGENTS.md` 应保持原样。应用后运行 `/control:status` 和 `/control:doctor`，确认两篇论文关联的是原来的 code，再像前面那样用 `git -C 论文路径 rev-parse --show-toplevel` 查看各自独立的 Git 根目录。

这些绑定不会生成论文正文、模板或参考文献库，它们先把材料归属说清了。LaTeX 是论文排版方式，可以先把 paper 理解为每篇文章专用的目录和版本历史。以后提交程序时，不需要清理这两篇文章的草稿；移除一篇论文的绑定也只解除关系，目录和 Git 数据仍然保留。一开始就有论文的项目，可以直接选择 LaTeX 初始化结构，详见 [仓库与论文指南](../extensions/control-init/README.md)。

算法需求仍在原 KM Plan 中维护。只有你现在明确准备为独立的写作工作另建计划，才输入例如 `/plan:new 为 paper-a 整理论文提纲，先做计划，不写正文`。助手保存后应出现不同路径和身份，原 KM 文件仍在。查看完提纲，用 `/plan:open 原KM计划的实际路径` 回来；批准提纲也不等于已经要求开始写文章。

## 把别人需要的用法留下来，再准备交付

研究材料有了归属，但同事拿到 code 时，不会同时拥有你的 control、聊天和论文草稿。他需要知道怎样编译、怎样输入矩阵，以及程序为什么只输出一个总权值。若项目还没有文档，就从 code 的 README 补上这些最必要的说明和一个完整例子；已有说明则原位替换过时的段落。之前接口稳定时改过文档，到了交付前还要核对一次相关变化有没有遗漏。

这里的“相关”包括已经提交、但还没交付的那部分。PR 可以理解为把一组提交交给人审阅的申请，它提供了定位这组变化的线索。让助手先确认实际 PR 的 base/head，也就是比较的起止提交，再加上属于这次交付的本地未提交文件；只看此刻 `git diff` 的剩余内容，会漏掉刚才已提交的修改。堆叠 PR 各自对照自己的基点，多 PR 的共同交付还要看最终净变化。PR 描述用来找路，判断接口仍要读实际 diff。

小项目通常按这个规则直接检查就够了。若文件增多后，模型经常找不到该改哪份说明，可以请它使用可选 DocSync 助手：

```text
请检查 KM 这次交付涉及的文档。先确认相关提交范围和本地修改，
再按实际实现路径与 README 的关系调用 docsync_check，
给出相关位置和仍不确定的问题。不要只根据 PR 描述判断。
```

调用参数和完整例子见 [文档检索指南](../extensions/task-plan/docsync/delivery.md)。刚初始化还没有任何提交时，应先正常完成首次提交，再使用这类 Git 检查。已有提交、只查本地相关修改时，可以使用 `ranges: []` 并列明 `localPaths`；实际 PR 则使用已核对的范围。助手应能说明候选来自哪处变化、指向哪份文档，并给出必要引用或未解决问题。

比如你约定了“输入输出改动对应 docs/cli.md”，却还没创建那篇说明，缺失应该留在问题里，接着由你决定补文档还是修正映射。它不要求先给全工程的文档加标记，没有配置文件也能直接提供对应关系。空候选不证明全仓库没有遗漏，README 出现在候选中也不证明文字正确；仍要对照当前接口阅读，确认例子已经只输出总权值。

如果你还担心最后一步忘记检查，可以在当前仍待完成的大任务上绑定本会话的 `watch`，让程序记得提醒。之后通过 Plan 工具完成这个已有大任务，包括最后一个子任务触发汇总时，应出现单独的文档提醒，Plan 正文没有新增检查结果。其他子任务不用每次提醒。关闭提醒或重启会清除绑定；手改 checkbox、任意 shell 提交和独立受治理 finalize 不经过这个入口，所以准备 PR 时仍应显式检查相关范围。提醒失败会显示问题，但不阻止普通完成，它目前不是强制文档门禁。

相关实现、验证和说明都核对后，按工作规则把小而完整的修改组成可审阅提交，产品改动进 code，验证记录进 control，PR 中对应两边的具体提交。初始化生成的 `AGENTS.md` 会提醒这些约定，但不会替你执行 Git 操作或拦截所有命令；合并、发布和破坏性操作仍由人另行决定。到这里，别人可以从 code 的说明开始使用程序，你也能从 control 的 Plan 继续下一项研究。

## 项目还会继续，工具也可以更新或停用

再过一段时间，工具发布了改进。Git 来源安装使用 Pi 管理的本地副本，远端合并后不会立即出现在当前会话；退出 Pi，在终端更新同一来源，再启动：

```bash
pi update https://github.com/FreeGrid/human_in_loop_code
```

本地路径安装则先更新那份检出，再重启 Pi。包更新不会自动重写你项目里的 `AGENTS.md`。需要采用新版工作规则时，按 [规则更新步骤](../extensions/control-init/README.md#更新现有工作空间的规则) 显式预览和应用；对照更新前后的文件，检查标记外的人工内容保留、绑定没变，再运行 doctor。这样工具可以升级，项目里的人工约定也有机会被认真看一遍。

只想暂时停用扩展，回到终端用 `pi config` 调整开关。要移除整个包，使用安装时的同一个来源：

```bash
pi remove https://github.com/FreeGrid/human_in_loop_code
```

卸载不会删除 control、code、论文、Plan 或 Git 历史。你的 matching 项目仍是几份普通文件和独立仓库；下次回来，打开那份当前有效的 Plan，就能看到已经做过什么、还有什么需要继续。
