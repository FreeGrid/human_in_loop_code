# 从零开始：和助手一起完成 matching 项目

[返回首页](../README.md) · [仓库与论文指南](../extensions/control-init/README.md) · [遇到问题](troubleshooting.md)

假设你准备做一个与匹配算法有关的研究，先需要一段不超过百行的 C++ 程序：把两组对象一一配对，让总得分尽可能高。你希望模型帮忙写代码，却不希望几轮讨论之后，程序旁边堆满计划、测试记录和论文草稿；更不希望它写完一大堆东西，你才发现双方理解的需求不同。

我们就从这个名为 matching 的小项目开始。第一天，让助手能工作，建立仓库，把需求说清，再完成一小步；第二天，带着同一份计划回来，检查实现。等程序要交给别人用、研究开始形成论文时，再引入文档、协作和更强的检查。跟着做的时候，可以把屏幕上的结果和文中的例子对照着看；哪一步卡住了，就从那一步的提示继续找原因。

## 先让助手在电脑上工作起来

先分清你接下来会用的两个输入窗口。**终端**用来启动程序，macOS 可以打开“终端”应用，Linux 使用自己的终端。**Pi**是在终端里运行的助手界面，负责连接模型，并让模型调用读写文件、执行命令等工具。这样的模型会话也叫 Agent。你可以把 Pi 想成工作台，把模型当作坐在工作台前的助手：装好工作台以后，还要接上一个可用的模型服务。

下文标为 `bash` 的代码在终端执行；标为 `text` 且以 `/` 开头的命令，在 Pi 输入框里输入；普通中文示例则是直接对助手说的话。比如 `cd` 是终端里切换目录的命令，`/control:init` 是进入 Pi 以后才使用的命令。

先安装 [Node.js](https://nodejs.org/en/download) 和 [Git](https://git-scm.com/downloads)。Node.js 提供运行 Pi 的环境，也带有下面要用的 `npm` 安装命令；Git 为文件保留版本记录。这里采用已验证目录切换的 Pi **0.84.4**，要求 Node.js **22.19.0 或更高版本**。本文终端示例按 macOS/Linux 编写，Windows 用户先看 [Pi 的平台说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/windows.md)。

```bash
node --version
git --version
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@0.84.4
pi --version
pi
```

看到 Pi 界面后，输入 `/login`，选择你已有账号支持的提供方并登录；也可以按提供方说明设置 API Key。接着用 `/model` 选择可用模型，发一句普通问题，看看能否收到回答。自部署服务先在 `~/.pi/agent/models.json` 登记地址和模型，具体例子见 [模型指南](models.md)。`~` 是你的用户目录，密钥也留在这里的个人配置或环境变量中。使用其他 Pi 版本时，安装与登录细节可以对照 [Pi 官方入门](https://github.com/earendil-works/pi/tree/main/packages/coding-agent#quick-start)。

能聊天之后，退出 Pi，回到终端安装本工具包：

```bash
pi install https://github.com/FreeGrid/human_in_loop_code
pi config
```

在配置界面找到 `control-init`、`task-plan`、`collaborating-agents` 三个扩展，以及 `collaborating-agents-system` 技能，把它们启用后按 `Esc` 返回。扩展增加命令和工具，技能提供协作说明。以前装过 Pi 示例 `plan-mode` 的话，顺手把那一项关掉，让这次的计划交给 Task Plan 管理；其他扩展照常使用。配置操作见 [Pi 包管理文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)。

如果你已经下载了本仓库，也可以把安装来源换成 `pi install /绝对路径/human_in_loop_code`，两种来源选一个即可。历史 npm 名称 `@baochunli/pi-collaborating-agents` 和原上游地址可能还没有本文的新功能，因此这里统一使用 FreeGrid 的 Git 来源。

第一次体验，先让规划和执行都沿用你刚选好的模型。在终端重新启动：

```bash
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

这行命令让 Task Plan 在这次 Pi 会话里沿用你选好的模型，Plan 功能和原来的 thinking 设置照常使用，想换模型时仍然可以打开 `/model`。这里的 `0` 只关闭**自动模型切换**，下次启动要继续这样用，就保留这段前缀。直接运行 `pi` 时，扩展会尝试默认的自部署 Qwen 预设；找不到模型就提示切换失败，接着沿用当前模型。后面有需要时，我们再配置三个阶段。

现在输入 `/control:status`、`/plan:status`，再打开 `/agents` 看一眼，按 `Esc` 返回。还没建工作空间和 Plan，看到“未找到”很正常。如果显示的是“未知命令”，就回头检查安装来源、扩展开关和是否重启。接着让助手做一件很小的实事：

```text
帮我用 shell 工具运行一下 pwd，把返回的目录显示出来。这次只查看。
```

留意屏幕上的 shell 调用，看看 `pwd` 真正返回了哪个目录。有了这条返回，才知道助手已经能动用工具。如果它只用文字告诉你“我在某目录”，可以再提醒它实际运行一次。能聊天却调用不了工具时，从模型连接、认证和工具调用配置查起；命令不见了则看 [排障入口](troubleshooting.md#输入命令没有出现功能)。后面检查代码和测试时，我们也会这样顺手看一眼工具的真实返回。

## 先给 matching 建一个清楚的家

助手已经能调用工具，现在可以安排项目文件的归属了。退出 Pi，在终端建立一个容纳项目的父目录，然后从这里启动：

```bash
mkdir -p ~/research/matching
cd ~/research/matching
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

在 Pi 输入：

```text
/control:init
```

选择 `Recommended — control + code`，再选择从工作空间名称创建仓库，名称填 `matching`。向导会加好后缀，准备同级的 `matching_control` 和 `matching_code`：前者放计划、测试和研究过程，后者放程序、运行资源和给使用者看的说明。先把这两份安顿好，论文目录等真正开始写文章时再加。

走到最后的预览时，先看实际路径。如果发现自己从错误的目录启动了 Pi，取消这次初始化，回到正确位置再来就好。取消后可以去目录里看一眼，确认刚才准备创建的文件夹和规则文件还没出现，已有工程也还在原处。路径看对了，就选 `Apply the shown initialization`。遇到 `preview-stale`，说明预览期间文件或仓库信息又变了；重新打开向导，看过最新预览再决定。

如果 matching 本来就是一个已有代码工程，这一步改选“使用已有目录”，填入 control 和 code 的实际路径。绑定前后各看一次已有文件和 `git status --short`，确认手头的代码、还没提交的修改都在原处。这次主要增加的是仓库关系和工作规则；已有目录还没用 Git 的话，向导会询问是否在原地建立版本记录。旧工程里混放的资料，可以等绑定完成后再慢慢整理。

如需用 Herdr 管理所有子 Agent，改用 `/control-init-herdr`，并按 [Herdr 初始化说明](../extensions/control-init/README.md#用-herdr-管理子-agent) 安装 skill。原 `/control:init` 继续保留 Pi、Codex、Claude 各自的原生协作机制；Herdr 模式则统一使用 Herdr。

应用成功后，Pi 会带着当前对话进入 control。先运行 `/control:status` 和 `/control:doctor` 看看两份仓库的路径，有提示就顺着它指出的位置检查。再让助手运行 `pwd`，并用相对路径读一下 `CONTROL_INDEX.json`。把返回的目录与 control 路径对上，再看看关系表里是不是刚才那两份仓库，这样就连文件工具的工作位置也一起确认了。

还可以另开一个终端窗口，查询两份仓库的根目录：

```bash
git -C ~/research/matching/matching_control rev-parse --show-toplevel
git -C ~/research/matching/matching_code rev-parse --show-toplevel
```

把两次输出放在一起看：一条是 `matching_control` 的完整路径，另一条是 `matching_code` 的完整路径。若都指向同一个父目录，就需要回去检查仓库绑定。再打开目录看看，关系表和 `AGENTS.md` 工作规则放在 control；新建的 code 还留着给程序用，计划、测试证据和论文草稿都有各自的去处。这一步建好的是本地仓库，后面每完成一小步工作，就可以把那部分提交下来；GitHub 远端等需要协作时再安排。

用一句中文让助手创建工作空间也可以。这种方式建好目录后还差一步：按提示在 Pi 输入 `/control:enter`，把会话转到 control。走斜杠向导后如果仍停在旧目录，也可以输入 `/control:enter /完整路径/matching/matching_control`，再用 `pwd` 看看是否已经到了正确位置。

## 写代码前，先确认它理解的是同一件事

目录安排好了，我们终于可以说需求。KM 是这个例子采用的匹配算法；即使你不熟悉它，也可以对照输入、输出和边界，判断模型有没有擅自增加东西。在 Pi 输入：

```text
/plan 实现一个不超过 100 行的 C++17 单文件 KM 程序，求 n×n 完全二分图的最大权完美匹配。整数权值允许负数。输入 n 和权值矩阵，输出总权值和匹配结果。不支持缺边、非方阵和非完美匹配。
```

这里的方阵表示两侧对象数量相同，“完全”表示每一对都有权值，“完美匹配”要求每个对象都配上。允许负权很关键：即使所有得分为负，也得完成配对。所以这类输入算出一个负数，完全可能是正确答案。

打开工具返回的 Plan 文件。它在 control 的 `plans/` 下，名字可能类似 `001-km.md`，照着返回的路径找就好。**把当前需求和每一条任务完整读一遍。** 对着刚才的请求，看看单文件、C++17、100 行以内、负权和输出要求有没有遗漏。如果多了一个规模上限、一份性能报告，或者别的交付任务，先想想自己是否真的需要。比如你可以说：“性能报告这次用不上，先把它从当前计划里去掉，专心完成这个小程序。”现在还在对需求，也顺手看一眼 code 的文件和 Git 状态，确认助手停在规划这一步。

Plan 的样子很简单：开头是格式标识和标题，接着是一段当前需求，下面列出大任务和一层子任务，用方框记录进度。眼前的工作写清楚，近期任务逐渐细化，远处先留个轮廓；一个小需求可能只有一个大任务。要是同样的意思又在 Strategy、Acceptance 等章节重复了几遍，可以请助手把它们整理回一份当前需求。模型写代码常常比人读代码快，此刻花几分钟把短计划看懂，后面就少一些返工。完整例子见 [Task Plan 指南](../extensions/task-plan/README.md)。

## 先做一小步，再看它是否真的完成

读到这里，你觉得计划已经把自己的意思说清了，就可以告诉助手开始。第一次把停点说具体一点，方便看清进度是怎么记下来的：

```text
按当前计划开始执行。实现放在 code，测试与验证放在 control。
先完成当前第一个有实际意义的子任务，用进度工具记录，然后停下来让我查看。
工作很小的话，直接保留一个大任务就好。
```

如果当前大任务有几个子任务，先打开 Plan 看看：做完的第一项打上了 `[x]`，大任务因为还有工作待做，继续留着 `[ ]`。`/plan:status` 可以快速看大任务进度，想看子任务就打开这份 Markdown。对得上实际工作以后，再让助手继续。偶尔模型把“继续”理解成继续解释，迟迟没有动作，这时直接输入：

```text
/plan:next
```

这个命令把当前需求、任务和下一项工作交给助手，接下来就能继续做事。通过进度工具勾选最后一个待办子任务时，程序会顺带勾选所属的大任务，**已完成子任务的文字和顺序仍然保留**。下一步轮到文件中第一个未完成的大任务，就在原处补上细节。回头看时，还是那份需求和任务树，做过的事情一项项留着；运行结果和检查过程则在 control 的执行记录里。

等核心算法和输入输出都能用了，让助手编译一次，把命令和返回展示出来。编译器负责把 C++ 源文件变成可运行的程序；如果电脑里缺少支持 C++17 的编译器，就先把环境装好，再回来运行。测试脚本、临时验证产物和过程记录留在 control。现在可以试试这组数据：

```text
2
-1 -4
-3 -2
```

这组数据只有两种完整配对，得分分别是 `-1 + -2 = -3` 和 `-4 + -3 = -7`，所以最大总权值是 **-3**，配对是第 1 行配第 1 列、第 2 行配第 2 列；接口从 0 编号时，就是 0→0、1→1。我们已经亲手算出了答案，现在把程序的实际输出拿来对照就很直观了。

假如程序输出了 0，就把这个结果交给助手：“这组数据每个对象都得配上，正确答案是 -3，帮我找找哪里出了问题。”让它在原 Plan 里重开相关工作，修好以后再跑一次。通过进度工具重开一个子任务，所属的大任务也会跟着重开，其他已完成的子任务继续保留。你回头看这份文件，就知道哪一部分正在返修。

勾选是帮你记进度的。你觉得某项已经做完，也可以自己勾上；至于编译、测试和审阅做到了哪一步，还要看各自的实际记录。比如输入 `/plan:task T001 done`，勾上的是这个大任务，它下面的子任务保留原状态，T001 换成你的实际任务 ID 即可。在外部编辑器里改勾选时，父子进度也由自己照看；需要程序汇总就用进度工具，详见 [状态规范](../extensions/task-plan/v3-format.md)。刚才的小样例查过了负权，接下来还得看看单文件、行数和其余输入边界。按真正做完的工作记录进度，才方便明天回来接着做。

## 用起来才发现，输出可以更简单

看到第一次结果后，你发现后续批量实验只会读取总得分，暂时不需要配对明细。需求在使用中变清楚很正常，接下来直接修改同一份 Plan：

```text
/plan:edit 现在只输出最大总权值，不再输出匹配结果；其他要求保持不变。
```

再打开原文件，看看路径和 `plan_id` 还是不是刚才那一份，输出要求有没有换成“只输出最大总权值”。旧的配对要求在这里被新想法替换掉，读起来就只有一个明确答案。接着看看输入输出任务：已经做过的部分现在要返工，通过工具修改定义后会回到 `[ ]`。可以让助手一并说清这次影响哪些任务，保留无关的算法进度；影响暂时拿不准时，先多重开几项，再一起核对。

这时让助手只讲本次改了什么、影响哪几项，读起来会轻松很多。确认理解一致后，再让它实现修改，重跑刚才的输入：这回只看总权值 -3 就够了。等接口稳定下来，顺手更新 code 中已有的输入输出说明，让例子也跟着换成新用法。以后再想到相关需求，继续改这份 Plan 就行，已经全部勾完也能接着改；真正准备另开一项工作时，再用 `/plan:new`。

## 第二天，从同一份 Plan 接着做

今天可以先停在这里。记下 control 和 Plan 的实际路径，退出 Pi。第二天从终端直接进入原 control，再启动即可：

```bash
cd ~/research/matching/matching_control
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

如果已经从别处启动了 Pi，在 Pi 中输入完整路径：

```text
/control:enter /完整路径/matching/matching_control
```

把示例换成机器上的真实路径。刚初始化的那次会话记得目标位置，可以省略路径；第二天重新启动，就把完整路径告诉它。以后进入同一个项目，用 `/control:enter` 就够了。若你用了 `--no-session`，会话保存已经关闭，这时回到终端，按提示用 `cd ... && pi` 从 control 启动即可。

进入后，先让工具实际运行 `pwd`，确认仍在 control，再用 `/plan:open plans/001-km.md` 选择昨天那份文件，文件名换成实际值。这一次先不让它写代码：

```text
先只看 AGENTS.md 和刚打开的 Plan，帮我讲讲现在要做什么、
哪些已经做完、接下来做哪一步。这次先只查看，我们对一下理解。
```

这正好是一次理解检查。把回答和 Plan 对着看，留意它讲的输出是不是只有总权值，昨天做完的子任务有没有读出来。如果它仍在讲最初的配对输出，或者说不清下一步，就先一起把文件里的当前需求理顺。对齐以后，有待办就输入 `/plan:next`；已经全部做完时，命令会告诉你没有待办，可以等新的需求来了再继续。这份 Plan 越清楚，换一天、换一个会话接手就越轻松。

## 准备给别人看，换一个角度检查实现

接下来你想把程序给同事用，便想再找找自己可能漏掉的问题。在当前会话输入 `/plan:review 关注负权、完美匹配和当前输出要求`，让助手先做一次只读检查。看它指出了哪个文件、哪段实现，以及为什么有问题；你看过这些意见以后，再安排需要的修复。此刻先把注意力放在问题上，代码和 checklist 留到实施时再改。

到这里，规划、执行和审阅三个阶段都有了用武之地。前面一直用 `PI_TASK_PLAN_MODEL_SWITCH=0 pi` 启动，Task Plan 就一直沿用手选模型。想给三个阶段分别挑模型时，再按 [模型指南](models.md) 登记可用模型、设置阶段变量，然后从加载了新环境的终端启动 Pi。下一次实际用到 `/plan:edit`、已经授权执行的 `/plan:next` 和 `/plan:review` 时，留意 Pi 显示的模型与 thinking 设置，对照 planning、normal、review 的配置看看是否选对。

三个阶段配的是同一个模型，屏幕上的名字自然也一样。预设 ID 写错或认证没配好时，扩展会提示切换失败，继续用当前模型，等方便时再修配置就好。自部署 Qwen/vLLM 的朋友可以再看看请求和服务日志：当前接入方式把 high 和 medium 都转换为开启 thinking，两者使用同一个开关，并没有分别设置推理预算。想知道服务实际怎样执行，从日志里核对会更踏实。

刚才的普通审阅还在原会话里，换模型也会保留这段上下文。如果你想让另一个会话专门看负权处理，可以把这一小块工作交出去：

```text
/subagent 阅读 ../matching_code 中的 KM 实现，只检查负权处理，报告具体位置和理由，不修改文件。
```

打开 `/agents`，就能跟着子任务的运行名称查看状态，等它做完，答复会回到原会话。读一读它引用的文件和理由，也看看文件是否保持原样——这次交出去的是只读工作。审阅意见拿回来之后，再由你或负责协调的助手判断怎么处理。审阅是否独立，要看会话如何建立、做了哪些实际检查，角色名字只是帮助分工。

如果等了一会儿还想看看进展，就让助手用返回的 Run ID 查询 `session` 或 `tail`。Run ID 是这次子任务的运行编号，用它可以直接找到相关记录。刚启动时看到 `session pending`，等登记完成后再查；一批任务里有多个子 Agent，就选具体的那个编号。先用普通后台方式就能体验分工，已经配置 cmux、并在其中运行主 Pi 的人，也可以打开可见面板。具体操作见 [协作指南](../extensions/collaborating-agents/README.md)。

用上一阵后，如果你发现模型经常漏看失败，或团队想把验证和独立审阅作为交付的固定条件，就可以考虑受治理 Harness，让程序负责把住这些环节。刚安装时，`/plan:governed status` 通常会显示尚未配置，这时继续用普通 Plan 就好。团队接好以后，可以在隔离环境故意让一次测试失败，再尝试 finalize，也就是正式结束任务；程序会拒绝这次接受，并说明还缺什么。授权失效、独立审阅缺失时，也用同样的方式检查。把这些服务接好需要一些准备，具体见 [Harness 的范围](harness.md) 和 [受治理步骤](../extensions/task-plan/v3-governed.md)。

## 同一份代码，开始支持两篇论文

假设后来研究有了两个写作方向：一篇介绍匹配方法，另一篇用它分析应用数据。程序仍是同一份，你希望两篇文章各自改稿、各自投稿，不把稿件塞进 code。现在回到 control，在 Pi 中运行：

```text
/control:update
```

选择 `Add one paper repository`，给第一篇填短 ID `paper-a` 和具体路径，例如 `~/research/matching/matching_paper_a` 对应的完整路径；第二篇同样添加 `paper-b`，用另一个目录。每次先看预览，路径错了就取消，回头看看原关系表和 `AGENTS.md` 还保持着更新前的内容。应用后用 `/control:status` 和 `/control:doctor` 查看两篇论文是否都关联到原来的 code，再像前面那样，用 `git -C 论文路径 rev-parse --show-toplevel` 看看各自的 Git 根目录。

现在每篇论文都有了自己的位置，正文、模板和参考文献库可以接着往里面准备。LaTeX 是论文排版方式，还不熟悉的话，先把 paper 理解成这篇文章专用的目录和版本历史就好。以后提交程序修改，这两篇文章的草稿仍安稳地待在各自仓库。哪篇文章暂时撤下，也可以移除它的绑定，目录和 Git 数据照样保留。一开始就有论文的项目，可以直接选择 LaTeX 初始化结构，详见 [仓库与论文指南](../extensions/control-init/README.md)。

算法需求继续在原 KM Plan 中维护。现在若准备为论文提纲单独做一份计划，可以输入 `/plan:new 为 paper-a 整理论文提纲，先做计划，不写正文`。助手保存后，看看新文件的路径和身份，再确认原 KM 文件也还在。提纲看好以后，等你明确说开始，再进入写作；想接着做算法，就用 `/plan:open 原KM计划的实际路径` 回来。

## 把别人需要的用法留下来，再准备交付

研究材料有了归属，现在试着站到同事那边看看：他手里只有 code，怎样才能把这个程序用起来？他需要知道怎样编译、怎样输入矩阵，以及为什么结果只有一个总权值。项目还没文档的话，就从 code 的 README 写起，补上这些最必要的说明和一个完整例子；已经有说明，就把旧段落改成当前用法。前面接口稳定时改过文档，到了交付前再看一遍相关变化，往往还能发现一两处顺手补上的地方。

检查时，把已经提交、但还没交付的修改也带上。PR 可以理解为把一组提交交给人审阅的申请，它正好提供了这条线索。让助手找到实际 PR 的 base/head，也就是比较的起止提交，再补上这次还没提交的相关文件。如果只看此刻 `git diff` 剩下的内容，刚才已提交的修改就容易漏掉。几个 PR 前后叠在一起，各自对照自己的基点；它们一起交付时，再看一遍最终净变化。PR 描述帮你找到入口，接口究竟变了什么，接着看实际 diff。

小项目通常按这个规则直接检查就够了。若文件增多后，模型经常找不到该改哪份说明，可以请它使用可选 DocSync 助手：

```text
请检查 KM 这次交付涉及的文档。先确认相关提交范围和本地修改，
再按实际实现路径与 README 的关系调用 docsync_check，
把实际 diff 和对应说明放在一起核对，告诉我哪里需要补、哪里还拿不准。
```

调用参数和完整例子见 [文档检索指南](../extensions/task-plan/docsync/delivery.md)。这个助手需要仓库里已有 Git 提交，刚初始化的项目可以先按正常流程完成首次提交。已有提交、只想查本地相关修改时，用 `ranges: []` 并列出 `localPaths`；有实际 PR，就填入核对过的范围。拿到报告后，看看每处候选是从哪个改动找来的、连到了哪份文档，再顺着给出的引用继续读。

比如你约定了“输入输出改动对应 docs/cli.md”，却还没写那篇说明，报告里就会留下这个缺口。你可以补上文档，也可以把映射改到已经有说明的 README。先给出文件之间的对应关系就能开始，配置文件和文档区块标记可以按需要再安排。看到空列表时，回头看看搜索范围和映射是否合适；找到了 README，就把相关段落和当前接口对一下，看看例子是不是已经只输出总权值。定位之后这一步阅读，仍要由人或助手来做。

如果担心忙起来忘记最后这次检查，可以给当前还没完成的大任务绑一个本会话的 `watch`。等你通过 Plan 工具完成它，或最后一个子任务带着大任务一起勾上时，程序就会单独提醒一次。Plan 里还是原来的需求和任务树，检查消息在旁边看就好。

这份提醒跟着当前会话走，关闭或重启后要重新绑定。它认的是 Plan 工具里的完成动作；手改 checkbox、在 shell 中提交、走受治理 finalize，都需要另外安排检查，所以准备 PR 时主动查一次相关范围最稳妥。检查没跑成，工具会把问题显示出来，普通勾选仍可继续；接下来怎样处理，由你和助手决定。

一路做下来，小而完整的修改已经陆续提交：产品修改在 code，验证记录在 control。把相关实现、验证和说明都看过以后，就可以准备 PR，写清两边对应的具体提交，审阅的人就容易找到依据。`AGENTS.md` 把这些约定留给后续助手，实际操作仍由人和助手完成；合并、发布以及删除之类的操作，等你另行决定。到这里，同事能从 code 的说明开始使用程序，你也能回到 control 的 Plan 继续下一项研究。

## 项目还会继续，工具也可以更新或停用

再过一段时间，工具又有了改进。Pi 使用的是自己管理的本地副本，把它更新后再启动，新功能就能加载进来。Git 来源安装可以在退出 Pi 后，回到终端更新同一个来源：

```bash
pi update https://github.com/FreeGrid/human_in_loop_code
```

本地路径安装就先更新那份检出，再重启 Pi。项目里的 `AGENTS.md` 有单独的更新步骤，安装包升级后，它仍保留你原来的约定。想采用新版规则时，按 [规则更新步骤](../extensions/control-init/README.md#更新现有工作空间的规则) 看过预览再应用；接着对比一下文件，看看标记外自己写的内容、仓库绑定都还在，再运行 doctor。这样工具可以往前走，项目积累下来的约定也能接着用。

只想暂时停用扩展，回到终端用 `pi config` 调整开关。要移除整个包，使用安装时的同一个来源：

```bash
pi remove https://github.com/FreeGrid/human_in_loop_code
```

停用以后，control、code、论文、Plan 和 Git 历史都还在原处。你的 matching 项目一直由这些普通文件和独立仓库组成；下次回来，打开那份 Plan，就能看见做过的事情，也能找到接下来要做的工作。
