# 从零开始：安装并完成第一个项目

[返回首页](../README.md) · [仓库与论文指南](../extensions/control-init/README.md) · [遇到问题](troubleshooting.md)

这份教程从一个空目录开始。你将建立彼此独立的 control 和 code 仓库，把“百行内 KM 算法”写成可读计划，再明确要求 Agent 开始工作。暂时不需要配置多 Agent、文档映射或受治理执行。先走通这一小圈，就能知道每个工具在什么时候出现。

操作后可以按文末的 [场景验证](#按场景验证你刚才完成了什么) 核对结果。安装、仓库、Plan 和续接对应主流程；论文、模型切换、文档助手和多 Agent 按实际需要选做。下面的命令和提示是给你在自己环境中操作的步骤，不表示你的环境已经验证通过。

## 终端、Pi 和模型，分别负责什么

终端是输入系统命令的窗口，macOS 可以打开“终端”应用；Linux 使用自己的终端。`cd` 用来进入目录，`mkdir` 创建目录。Pi 在这个窗口中运行，连接你选择的模型，并让模型调用读写文件等工具。模型服务可能来自一个在线提供方，也可能由你自己部署；安装 Pi 本身不会提供模型账号或运行模型的服务器。

下文标为 `bash` 的代码在**终端**执行，标为 `text` 且以 `/` 开头的命令在**Pi 的输入框**里输入。不要把 `/control:init` 当作终端命令。没有 `/` 的中文示例则可以直接作为给 Agent 的要求。

## 安装并确认 Pi 能回答问题

先安装 [Node.js](https://nodejs.org/en/download) 和 [Git](https://git-scm.com/downloads)。Node.js 是运行 Pi 的程序环境，会一起提供 `npm` 安装命令；Git 负责文件版本记录。这里的安装示例以已验证目录切换的 Pi **0.84.4** 为基准，它要求 Node.js **22.19.0 或更高版本**。Windows 用户先参考 [Pi 的平台说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/windows.md)；本文 shell 示例按 macOS/Linux 编写。

```bash
node --version
git --version
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@0.84.4
pi --version
pi
```

在 Pi 内输入 `/login`，选择你已有账号支持的提供方并完成登录；也可以按照提供方说明设置 API Key。接着输入 `/model` 选择可用模型，再发一句普通问题确认能收到回答。自部署服务需要先在 `~/.pi/agent/models.json` 登记地址和模型，配置入口见 [模型指南](models.md)。这里的 `~` 表示你的用户目录，配置属于你自己的 Pi，不能把真实密钥提交到项目仓库。

安装与登录方式以 [Pi 官方入门](https://github.com/earendil-works/pi/tree/main/packages/coding-agent#quick-start) 为准。本文核对的是上面的版本，不代表所有历史或未来版本行为相同。

## 安装这个工具包

退出 Pi 回到终端，安装本仓库：

```bash
pi install https://github.com/FreeGrid/human_in_loop_code
pi config
```

配置界面里应能看到并启用 `control-init`、`task-plan`、`collaborating-agents` 三个扩展，以及 `collaborating-agents-system` 技能。扩展增加命令与工具，技能提供协作时的工作说明。按 `Esc` 离开配置，再重新启动 Pi 加载它们。

如果以前安装过 Pi 示例 `plan-mode`，建议在 `pi config` 中禁用那一项，只保留这里的 Task Plan，避免两个计划功能同时影响操作。你不需要卸载其他无关扩展。源安装与开关的含义见 [Pi 包管理文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)。

已经把本仓库下载到本地的人也可以改用下面的来源。二者选一个，不要重复加载同一份扩展：

```bash
pi install /绝对路径/human_in_loop_code
```

历史 npm 名称 `@baochunli/pi-collaborating-agents` 与原上游 Git 地址仍然存在，但它们可能尚未发布本文的新功能。第一次体验这套完整流程，优先使用上面的 FreeGrid Git 来源。

## 给工作建立清楚的归属

先选一个用来容纳项目的普通目录。例如：

```bash
mkdir -p ~/research/matching
cd ~/research/matching
pi
```

在 Pi 中输入：

```text
/control:init
```

向导目前的按钮文字可能是英文。先选择 `Recommended — control + code`，再选择从工作空间名称创建仓库的选项，名称输入 `matching`。它会在当前目录下准备 `matching_control` 和 `matching_code`。名称中不用再加 `_control` 或 `_code`；如果目标已经存在，改用“使用已有目录”，不要强行重复创建。

向导最后会展示实际路径和将写入的文件。看清楚 control 保存管理过程、code 保存交付物以后，再选择 `Apply the shown initialization`。如果路径不对，可以返回修改；也可以取消。此时只建立本地 Git 仓库和工作规则，没有创建 GitHub 仓库，没有提交或推送你的文件。

成功后 Pi 会将当前会话续接到 control 目录，后续读文件和 shell 命令也以该目录为工作位置。你可以运行 `/control:status` 查看绑定，运行 `/control:doctor` 检查路径与规则是否一致。需要一开始就配论文，或者已有代码工程，请继续读 [Control Init 的具体例子](../extensions/control-init/README.md)。

自然语言也可以发起初始化，例如“创建一个名为 matching 的本地 control 和 code 工作空间”。这种工具调用不能在模型执行中直接替换会话，完成后按提示输入 `/control:enter`，再继续规划。

## 先读懂计划，再让模型执行

在 Pi 中输入以下完整需求。算法细节本身不是本教程的重点；这个例子刻意把输入、输出和边界说清，方便你判断模型有没有自行增加内容。

```text
/plan 实现一个不超过 100 行的 C++17 单文件 KM 程序，求 n×n 完全二分图的最大权完美匹配。整数权值允许负数。输入 n 和权值矩阵，输出总权值和匹配结果。不支持缺边、非方阵和非完美匹配。先做计划，暂不写代码。
```

Plan 保存在 control 下的 `plans/` 中，通常形如 `001-km.md`。它应是一段当前需求加一棵勾选任务树，而不是逐轮追加的分析报告。**把需求和每一条任务完整读一遍。** 发现多出的限制、文件或功能，先让它改计划。例如：

```text
仍然修改当前计划：不需要性能基准报告，不要增加额外的用户功能。
```

计划符合你的意思后，另行明确开始执行：

```text
按这份计划开始执行当前任务。实现放在 code，测试与验证放在 control。
```

后续可以说“继续”。自然语言的继续依赖模型调用正确工具；如果它没有行动，直接输入：

```text
/plan:next
```

这个命令给 Agent 当前任务和必要工作上下文；它不代表任务瞬间完成。执行时完成一个子任务就记录一个，所有子任务完成后程序汇总父任务。完成的子任务仍然保留。你可以输入 `/plan:status` 看短进度，也可以直接打开 Markdown。普通 `[x]` 表示当前认为完成，不自动表示测试或独立审阅通过。更完整的修改和状态规则见 [Task Plan](../extensions/task-plan/README.md)。

本工具默认预设了一个自部署 Qwen 模型标识。如果你的 Pi 没有登记它，会提示切换失败并保留当前模型，普通使用仍可继续。先只使用已经选好的模型时，可以在终端这样启动：

```bash
PI_TASK_PLAN_MODEL_SWITCH=0 pi
```

这行命令启动 Pi，并且只对本次进程关闭 Task Plan 的自动模型切换；Plan 和 thinking 都没有被关闭，仍然可以在 `/model` 手动选模型。要长期设置三个阶段，按 [模型指南](models.md) 配置，不需要改源码。

## 明天继续，不重新建立一遍

第二天最直接的做法，是在终端进入 control，再启动 Pi：

```bash
cd ~/research/matching/matching_control
pi
```

如果 Pi 已经在其他目录启动，可以在 Pi 中输入：

```text
/control:enter /完整路径/matching/matching_control
```

把示例替换成你机器上的完整路径。刚刚初始化的同一会话可以省略路径；重启后应明确提供。已经初始化过的仓库不需要再次运行 `/control:init`。若使用 `--no-session` 关闭了会话保存，就按扩展显示的 `cd ... && pi` 命令重新启动，不能通过会话续接切换目录。

接着明确指定要继续的文件，例如“阅读 AGENTS.md 和 plans/001-km.md，继续当前未完成任务”。普通 Plan 不依赖某次聊天的隐藏记录，所以换一个会话仍能看懂。切换工程时，应重新确认工作目录与所选 Plan。

## 交付前走完最后一小步

实现中的用户可见行为稳定后，就让 Agent 更新 code 中相关说明；准备交付当前大任务或 PR 时，再核对相关变化是否有文档遗漏。PR 可以理解为“把这一组提交交给人审阅的申请”。不是每个小任务都要再生成一篇报告；小而完整的提交组成一个可审阅的交付片即可。

初始化生成的规则会要求明确授权、按范围实施、验证后提交 PR，并把合并、发布和破坏性操作留给人单独决定。这些是给 Agent 的持久指令；Control Init 本身不会替你运行实现或 Git 发布。普通流程已经够用时，不需要额外搭建 Harness。需要程序提供文档候选位置时，读 [文档检索指南](../extensions/task-plan/docsync/delivery.md)。

### 场景 1：安装和模型连接

在终端运行 `pi --version` 和 `pi config`，确认 Pi 能启动，三个扩展及协作技能处于启用状态。重新进入 Pi 后，输入 `/control:status`、`/plan:status`，再打开 `/agents`。还没初始化或没有 Plan 时，显示“未找到工作空间/计划”这一类提示可以是正常结果；提示“未知命令”则说明对应命令还没加载。按 `Esc` 退出面板继续。

然后向模型发出一项只读请求：

```text
请实际调用 shell 工具运行 pwd，原样展示返回的目录，不修改文件。
```

应看到真实工具调用及返回，而不只是模型猜测目录。能普通聊天但不能正确调用工具，仍不足以证明模型接入适合后续操作；检查模型配置、工具调用解析或认证。命令缺失先检查安装来源、开关和是否重启，见 [排障入口](troubleshooting.md#输入命令没有出现功能)。

### 场景 2：新建仓库与真实工作目录

按前面的向导创建 matching 后，在 Pi 中运行 `/control:status` 和 `/control:doctor`。绑定应指向同级的 `matching_control`、`matching_code`，没有未解决的路径、身份或规则错误。若有警告，先读它具体指向什么，不以模型一句“健康”替代命令结果。

另外打开一个终端窗口，分别查询两个仓库的 Git 根目录：

```bash
git -C ~/research/matching/matching_control rev-parse --show-toplevel
git -C ~/research/matching/matching_code rev-parse --show-toplevel
```

应返回各自的完整目录，而不是同一个父目录。回到 Pi，要求它实际运行 `pwd`，再通过相对路径读取 `CONTROL_INDEX.json`；工作目录应为 control，读到的应是这份工作空间的关系表。这样同时验证绑定和真正的文件工具位置，避免“状态显示 control，但 shell 仍在旧目录”的问题。

control 中应有关系表和带管理标记的 `AGENTS.md`；新建 code 中不应因初始化而出现 Plan、测试证据或论文草稿。初始化后没有第一条提交或 GitHub 远端是正常现象，不能为了看到提交记录就认为需要重新初始化。未自动进入时使用 [已有仓库续接方法](#场景-8重启后仍知道在哪里做什么)。

### 场景 3：已有代码与多篇论文

如果选择绑定已有目录，操作前先记下几个已有文件的内容，以及 `git status --short` 显示的原有改动；操作后在相同目录再次查看。已有代码文件、原有未提交改动应保留，绑定指向你选择的路径，不应生成另一份同名代码来替代它。control 的关系表和规则是预期新增；已有非 Git 目录经明确批准后新增 Git 元数据也是预期变化。

需要两篇文章时，通过 LaTeX 初始化选项或 `/control:update` 的 `Add one paper repository` 分别添加 `paper-a` 和 `paper-b`，使用不同的实际路径。再运行 status/doctor，检查两篇论文均作为独立仓库关联同一份 code。可以像上一场景那样对每个论文路径运行 `git -C 路径 rev-parse --show-toplevel`，应各自返回独立根目录。

绑定成功不表示已经生成论文模板、正文或参考文献库；它确认的是归属结构。移除论文绑定的练习只解除关系，实际目录和 Git 数据应保留。若误选了目录，先取消预览，再按 [仓库与论文指南](../extensions/control-init/README.md) 修正，不通过删除原工程来重试。

### 场景 4：首次计划是否符合你的意思

执行前面的 `/plan` 请求后，打开工具返回的实际 Markdown 路径，不假定文件一定叫 `001-km.md`。逐条复述需求：C++17、单文件、不超过 100 行、方阵完全二分图、最大权完美匹配、允许负权、输入矩阵、输出总权值和匹配结果。对照原请求，看它是否遗漏边界，或额外增加性能报告、规模上限等未确认要求。

文件应只有格式标识、标题、当前需求和两层以内的任务树，不重复保存一轮轮 Strategy、Acceptance 或验证记录。眼前任务应足够明确，后面任务可以粗略，简单工作只有一项也有效。你要求“暂不写代码”时，不应已经开始实施；可以查看 code 的实际文件和 Git 状态确认。

还可以提出一次只读理解检查：

```text
只阅读这份 Plan，不依赖之前的聊天，复述当前需求、已完成项和下一项工作。暂不执行。
```

回答应能从文件中找到依据。若你自己读不懂，或模型必须补猜关键事实，先修正需求和任务，再开始写代码。

### 场景 5：新增需求修改原文件，明确新开才另建

在练习计划中记下路径和 `plan_id`，再提出一个真实的小变化。例如原来要输出配对，现在只想看总权值：

```text
/plan:edit 现在只输出最大总权值，不再输出匹配结果；其他要求保持不变。修改当前计划，先不执行。
```

再次打开原文件，路径和身份应不变，旧的输出要求被替换，输入输出相关任务同步调整。不能一处仍要求配对，另一处又说不输出；也不应因为补充需求多出一份 Plan。必要影响范围外的进度应保留；如果已经完成的相关工作被重新定义，通过工具修改后应重新打开。无法确定影响范围时可以先保守重开，再由人核对，而不是复用过期的完成判断。

练习完后可以把需求改回原要求。只有想验证“另建计划”时，再明确运行 `/plan:new`，提出一项独立的小需求。应产生新的路径和身份，原文件仍在。之后用 `/plan:open 原来的实际路径` 回到 KM 计划，避免在另一份计划里继续。

### 场景 6：子任务进度与 rolling

选择一个确实需要两个或更多子任务的练习任务，先核对每条子任务有实际含义。明确要求 Agent 完成当前第一个子任务，调用进度工具记录，然后停下来让你查看。若第一个已经完成但其他孩子仍待做，应看到该孩子为 `[x]`、父任务仍为 `[ ]`，兄弟任务和未来工作保持原状。

继续完成剩余子任务后，最后一次子任务状态更新应自动勾选父任务。孩子的文字与顺序仍保留。下一轮工作落到文件中第一个未勾选的大任务；准备做它时就在原处补必要细节，不追加“第二轮计划”或完成总结。`/plan:status` 是顶层简表，查看孩子请读实际 Plan。

还可以在练习副本中让 Agent 通过子任务状态工具重新打开一个已完成孩子。应同时打开父任务，其他已完成孩子保留。直接运行 `/plan:task T001 done` 是另一种人类选择：它勾父任务而不替你勾孩子，不能用它来测试子任务汇总是否工作。外部编辑器也不会自动经过这条工具规则。对照 [状态规范](../extensions/task-plan/v3-format.md) 判断，避免把正常的不同入口误当故障。

### 场景 7：实际执行结果与失败反馈

对已经明确授权执行的 KM 任务，让 Agent 展示真正的编译或运行命令及返回。验证脚本和过程记录放在 control，产品实现仍放在 code。对于“最大权完美匹配且允许负权”，可以使用下面的已知答案输入；具体送入程序的方法按实际输入接口执行：

```text
2
-1 -4
-3 -2
```

两种完整配对的总权值分别为 `-1 + -2 = -3` 和 `-4 + -3 = -7`，所以应输出最大总权值 **-3**。仍要求配对结果时，应是第 1 行配第 1 列、第 2 行配第 2 列（程序采用从 0 编号时对应 0→0、1→1）。如果前一场景已把需求改成只输出总权值，就按新要求检查，不再要求配对输出。

输出 0、只匹配部分顶点，或把失败运行说成通过，都不符合这条需求。编译成功也不能替代结果正确。还应按当前需求核对单文件、行数和其他输入边界；这个小样例只检查一部分情况，不能证明整个算法正确。

真的出现失败时，失败信息应反馈给 Agent，相关未完成工作保持待处理，修复后重新运行。普通 checkbox 可以手工修改，所以判断是否验证通过要看真实返回，不看 `[x]` 本身。证据和测试结果留在 control 的执行记录，不加进 Plan 正文。

### 场景 8：重启后仍知道在哪里、做什么

先记住 control 和当前 Plan 的实际路径，再退出 Pi。从另一个目录启动新 Pi，用完整路径 `/control:enter` 进入原工作空间。再次让工具运行 `pwd`，结果应回到 control；用 `/plan:open` 明确打开同一文件，需求、任务和已完成子任务应与重启前一致。

先只读复述下一项，确认正确后再 `/plan:next`。它应继续第一个待办，而不是重复已完成工作或新建计划。新会话缺少旧聊天记忆是正常的，Plan 应提供继续工作所需的当前理解。不要为了验证而把已完成进度清空。

另行使用 `--no-session` 时，无法通过持久会话续接切目录，提示你用 `cd ... && pi` 是正常边界。它不表示仓库初始化失败，按提示从 control 启动即可。

### 场景 9：关闭或开启自动模型切换

先在终端用 `PI_TASK_PLAN_MODEL_SWITCH=0 pi` 启动，在 `/model` 选好一个可用模型并记下。执行规划、普通工作或 `/plan:review` 后，Task Plan 不应自行把它换成某个阶段预设，Plan 的普通命令仍应可用。这个结果验证的是“关闭自动切换”，不是关闭模型思考。

要检查开启后的行为，先按 [模型指南](models.md) 配好真实可用的预设，在载入新环境的终端中启动 Pi。分别进入 `/plan:edit`、已授权的 `/plan:next`、`/plan:review`，核对 Pi 实际显示的模型和 thinking 设置是否符合 planning、normal、review。执行命令可能真正开始工作，应选择准备好执行的练习任务。

三个阶段配置了同一个模型时，名称不变是合理的，不能据此判定切换失败；可以在有其他可用模型时暂时为一个阶段设置不同预设再观察。无可用认证或 ID 错误时，应看到相应提示并保留当前模型，普通工作仍可继续。Qwen 当前映射中 high/medium 都打开 thinking，服务端是否按预期推理需看真实请求与服务日志，不能只看 Pi 的标签。

### 场景 10：可选文档检查与交付提醒

先完成普通文档更新：行为稳定后改对应说明，交付前核对相关变化。需要体验助手时，选择一个已有 Git 提交的练习 code 仓库，明确指出这次相关的改动与对应文档；让 Agent 依照 [DocSync 完整参数例子](../extensions/task-plan/docsync/delivery.md) 调用 `docsync_check`。

只查看本地未提交改动，可以使用 `ranges: []` 并列明 `localPaths`；实际 PR 则使用已核对的 base/head，已提交的相关变化也应包含。刚初始化、还没有任何提交的仓库，应先正常完成首次提交再使用这类 Git 检查，不通过编造基点来假装可用。

候选应能说明来自哪个相关变化、对应哪份文档，并提供必要引用或未解决问题。可以在练习请求的 mappings 中故意指向一份不存在的文档，检查报告是否明确留下缺失问题；不要为了试这个场景删除真实文档。空候选不表示全仓库已检查，已有文档被列出也不表示内容正确。没有配置文件时可直接提供 mappings，不需要先给所有文档加区域标记。

选择 `watch` 时，在同一会话通过 Plan 工具让对应已有父任务从未完成变为完成，应看到单独的文档提醒，Plan 正文没有新增检查结果。关闭提醒或重启后它不再持有原绑定；直接手改 checkbox、任意 shell 提交和独立受治理 finalize 不走这条提醒入口。检查失败仍应显示问题，但不会禁止普通完成，这就是当前助手的预期行为。

### 场景 11：可选多 Agent 协作

先派出一个有清楚范围的只读任务，例如前面协作指南中的负权检查。在 `/agents` 应能看到孩子的运行名称和状态，父会话最终收到结果。核对返回是否指出相关文件或问题依据，实际文件未被这个只读任务改动；名字叫 reviewer 并不自动证明它已独立验证。

需要查询细节时，用返回的 Run ID 查 `session` 或 `tail`。刚启动显示 `session pending` 可以是正常状态，等待登记；并行 batch id 有多个孩子时，应要求你选择具体孩子，而不是混读一份输出。只有已配置 cmux 且父 Pi 在其内部时再测试可见面板，普通后台模式已经可以验证分工与交接。操作与角色配置见 [协作指南](../extensions/collaborating-agents/README.md)。

### 场景 12：取消、更新与可选 Harness 的边界

取消练习可以在一个准备新建的示例工作空间里进行：走到初始化预览再选取消，计划中的目标目录和规则文件不应被本次操作创建。已有工作空间更新到预览后取消，原关系表和 AGENTS 应保持原样。再次正常应用时，只有审阅过的内容才应被写入；若提示 `preview-stale`，重新阅读实际状态，不把旧预览继续套上去。

更新工具包后，已有 AGENTS 不会自动换新。按 [规则更新步骤](../extensions/control-init/README.md#更新现有工作空间的规则) 显式更新时，检查标记外人工内容保留、绑定仍正确，再运行 doctor。删除绑定或卸载扩展也不应顺便删除用户仓库和 Git 历史。

最后，如果你没有接入受治理宿主，运行 `/plan:governed status` 应说明未配置，普通 Plan 仍可使用。已经接入的团队则应在隔离验证环境中检查失败验证、失效授权或缺少独立审阅是否阻止 governed finalize；这些不是普通安装后凭一个开关就能完成的测试。需要什么服务、能保证什么，见 [Harness 的范围](harness.md) 和 [受治理步骤](../extensions/task-plan/v3-governed.md)。

## 更新或停用

Git 来源安装在 Pi 管理的本地副本中，不会因为远端刚合并就自动出现在当前会话。Pi 0.84.4 可以针对同一来源更新：

```bash
pi update https://github.com/FreeGrid/human_in_loop_code
```

本地路径安装则跟随那份检出的文件；先让检出更新到需要的版本，再重启 Pi。安装包更新不会偷偷重写已有工作空间的 `AGENTS.md`，模板更新流程见 [Control Init](../extensions/control-init/README.md#更新现有工作空间的规则)。

只想暂时停用某一扩展时使用 `pi config`。要删除整个包，使用安装时的同一个来源，例如：

```bash
pi remove https://github.com/FreeGrid/human_in_loop_code
```

卸载只移除扩展加载关系，不会删除你的 control、code、论文、Plan 或 Git 记录。
