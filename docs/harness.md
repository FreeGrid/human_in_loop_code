# 什么时候需要 Harness，它能保证什么

[返回首页](../README.md) · [排障](troubleshooting.md) · [普通 Plan](../extensions/task-plan/README.md) · [文档检查](../extensions/task-plan/docsync/delivery.md)

如果模型足够听话，一段清楚的指令就能让它先更新计划、每做完一项记录进度、交付前检查文档。问题在于，模型可能漏掉某一步，也可能把“我认为完成了”当作真实验证结果。Harness 是围绕模型执行的程序机制：把能够明确检查的规则交给程序，把需要人判断的决定保留下来。

本工具选择逐层增加约束。第一次使用不必为了写一个小程序先配置签名密钥、沙箱和审阅服务；遇到实际遗漏或高要求交付时，再选择需要的层。缺少更强状态不会让普通功能失去可用性，但普通结果也不会因此自动带上更强保证。

## 三层工作，各自承担什么

| 层次 | 已有能力 | 仍需要什么 |
| --- | --- | --- |
| 普通 Plan | 读取与格式验证、局部更新、工具内父子进度汇总、定义修改后重开、过期写入检查 | 模型真正调用工具，人阅读需求与任务；外部编辑器维护自己的进度一致性 |
| 可选文档助手 | 相关 Git 范围、文档映射与引用、显式遗漏、会话内交付提醒 | 人或模型读相关变化并判断说明是否正确；它不是强制发布门禁 |
| 可选受治理执行 | 显式人类授权、范围与运行约束、真实验证、独立审阅、最终接受和恢复机制 | 受信任宿主提供真实执行与验证能力，配置正确的标准，并运行在支持条件下 |

这三层没有要求把所有信息都写进 Plan。Plan 仍是需求和 checkbox；执行记录、证据、权限、恢复信息留在它背后的内部运行时。手写 `[x]` 可以表示普通完成，但不能凭空生成受治理验证记录。

## 一个测试失败的例子

假设 KM 实现完成后，真实测试显示负权输入给出错误答案。普通流程中，Agent 应当看见失败、继续修复，并让未完成工作保持未勾选；但普通手工 checkbox 不被用来认证测试结果。如果模型忽略了失败，不能因为 Plan 上出现 `[x]` 就宣称验证通过。

在已经接好受治理执行的宿主中，验证结果与当前需求、执行和文件内容绑定。失败、越界修改、失效授权或缺少独立审阅会阻止该受治理任务 finalize。模型不能只发一个“passed”字符串绕过真实验证。修复后应重新验证，再获得绑定到这次结果的审阅和最终接受。

这能约束流程的证据条件，却不保证研究结论绝对正确。如果测试根本没覆盖负权，或人批准了错误的标准，程序也不能自动推导所有遗漏。更弱的模型尤其需要短而具体的任务、真实失败反馈和可检查标准；更强模型也不能把没有做过的验证说成做过。

## 隐藏合同会不会悄悄扩大需求

受治理任务在执行时可以生成严格的内部合同，包含当前需求、任务和子任务，以及可信策略指定的验证方法、可读写目录和允许执行的程序。合同的目的是落实已经确认的需求，不是借“安全”或“验收”之名增加产品功能。

例如允许写 `src/`，只表示有权限在这里实现当前任务，不表示用户同意再做一个命令行工具。突然增加“必须支持非方阵”或“额外输出性能报告”，应先更新需求并由人确认，不能只藏在验证策略里。精确引用和子任务覆盖检查能建立对应关系，但验证方法的实际含义仍需审阅。

## 普通安装后能不能直接打开强制模式

当前 V3 没有一个通用开关，可以自动为任何仓库补好完整的受治理服务。集成者需要提供持久密钥、运行目录、可信策略、真实沙箱、进程绑定的验证器和独立 reviewer。普通 `/plan:governed` 在未配置时会说明未配置，普通工作仍可继续。

当前沙箱约束的是 Darwin/macOS 上通过该路径启动的子进程，不隔离整个 Pi，也不等于支持了任意平台。完整存储被一起回滚时，还需要外部检测锚点；没有被内核观察到的历史编辑，也不能事后全知地重建。具体命令与集成要求见 [受治理执行指南](../extensions/task-plan/v3-governed.md) 和 [内核接口](../extensions/task-plan/v3-kernel.md)。

DocSync 还保留旧流程的事实与候选层，旧决策、欠账处置和受限 Maintainer 写入流程并未被当前轻量助手完整实现。不要为了减少提示遗漏，直接把旧 DocSync 设为 on 并期待有现成的完整强制流程。对已有大量代码而没有文档的工程，先补当前交付必要的说明和关联；以后若接强制策略，应要求必要问题得到处理，而不机械要求所有文件都有区域标记。
